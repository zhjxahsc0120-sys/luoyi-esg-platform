## 1. 设计问答（必须直接回答）

### Q1. 为什么主口径不应是「应备 4 项」？4 项与 11 类目录是什么关系？

**结论：** 主口径必须是 **11 类应备资料类别 + 具体文件归集进度**；所谓「4 项」只是 **待补齐子集（多对齐 G04 环境缺口）**，不是整包应备总量。

**依据：**

- V0.3 附录明确：弃用稀疏「应备 4 项」作标题；G04 约 4 项缺口映射为目录内「待补齐」。
- 当前 manifest：`categoryCount=11`，`requiredFileCount=46`，`pendingCount=4`；`00_资料目录及缺失说明` 与回答文案一致。
- 旧设计线框曾写「应备 4 项」，那是 **早期样例包文件预览**（目录+水保+问题摘要+核查表），不是监管迎检的完整证据链。

**建议调整：**

- 产品/前端：PackageCard 主 chips 继续用「类别/文件/已归集/待补齐/未闭环/闭环率」；禁止回退「应备 N 项」作为唯一标题（仅在无 stats 时兜底）。
- 资料：待补齐 4 项清单与 G04 名称保持可对账；若甲方清单变更多/少于 4，只改 pending，不改「11 类」主叙事。

### Q2. 「应对上级检查」与「部门自备迎检清单」产品表述差异？当前 UI/文案是否到位？

**结论：** 产品定位是 **面向上级监管/检查组的合规口径 + 可下载备检包**，不是「安环部/合约部自己列 checklist」。当前 **主路径文案基本到位**，局部仍可收紧。

**依据：**

| 维度 | 部门自备迎检（已弃用） | 应对上级检查（现行） |
|------|------------------------|----------------------|
| 主语 | 某部门要交什么 | 如何向上级检查组说明合规与备齐材料 |
| 包名 | `安环部_迎检资料包_…` | `上级检查_环保/安全/综合合规资料包_…` |
| 同答结构 | 仅清单 | 库口径结论 + 表 + 下载资料包 |

- 欢迎 chip 已有「应对上级检查」；推荐问含 C03/C04/C05。
- 回答 content 以「应对上级环保检查…」起句；dataBasis 写明「不以应备仅 4 项作为主口径」。
- 个别占位文件正文仍写「迎检资料包占位归档件」——语气偏「内部归档」，可改为「上级检查备检材料占位」。

**建议调整：**

- 产品：对外演示话术统一用「应对上级××检查 / 合规资料包」，禁用「部门迎检」。
- 资料：批量替换包内 md 首段「迎检」为「备检/上级检查」口径（不改目录结构）。

### Q3. E02「首页 5 vs 曾助手 0」根因？用 formal 还是与首页同源 demo 闸？长期如何？

**结论：** 根因是 **scope 不一致**（首页走 `E02_ALLOW_DEMO=1` 的 demo 台账有数，助手曾默认真查 formal → 空）。现已改为 **与首页同源闸**；长期应 **正式库灌数后默认 formal**，demo 闸仅作显式开关。

**依据：**

- `mysql_api.E02_ALLOW_DEMO` 默认环境变量为 `"1"` → 首页 KPI 读 demo。
- 助手现：`_e02_homepage_scope()` → `"demo" if E02_ALLOW_DEMO else "formal"`，再 `get_e02_issues` / 闭环率 SQL 同 scope。
- 「首页 5、助手 0」典型复现：助手进程 `E02_ALLOW_DEMO=0`、或旧代码写死 formal、或未重启仍跑旧 builder。

**建议调整：**

| 阶段 | 建议 | Owner |
|------|------|-------|
| 现演示校核 | 保持助手与首页 **同一闸**；校核前确认两端环境变量一致并重启后端 | 后端/运维 |
| 产品拍板 | 明确默认对外口径是 formal 还是允许 demo | 产品 |
| 长期 P0 | 向 formal 灌入与首页一致的未闭环事项；演示环境才开 `E02_ALLOW_DEMO=1` | 后端/资料 |

### Q4. 资料包权威源是什么？当前是「通用占位」还是「项目批复落地」？缺口？

**结论：** **权威源应是** 罗宜环评报告书及批复、水土保持方案批复、甲方上级检查/合规核查清单，以及平台 E02/G04 运行态缺口。**当前包 = 通用检查逻辑 + 罗宜命名的占位文件**，**不是**批复条文驱动的落地件。

**依据：**

- 01 类文件名含「罗宜高速环境影响评价批复」等，但正文为短占位说明，非批复扫描件/条款摘录。
- README：`文件为占位 csv / md / txt，结构示意用；数值非正式业务黄金数`；manifest `nature: "sample"`。
- 待补齐项用「对齐 G04××」注释，属平台缺口映射，非甲方纸质清单逐条对账结果。

**缺口：**

1. 无真实 PDF/扫描件与文号、批复日期、落实条款对照表（有「落实台账」占位，无条款级勾选）。
2. 应备 46 项未从批复「三同时/监测频次/水保措施」条文重算。
3. 甲方检查清单未作为 inventory 权威输入源（现为人工编目）。

**建议调整（P0 · 资料）：** 用真实环评/批复/水保/甲方清单替换文件名与应备数；占位 md 逐步换成原件或「摘要+原件路径」；manifest 重算后同步 zip。

### Q5. 统计指标各自定义与数据源？哪些实算、哪些静态？

| 指标 | 定义 | 数据源 | 实算/静态 |
|------|------|--------|-----------|
| **应备资料类别 11** | 标准目录 01–11（00 为总说明，不计入「11 类」） | manifest `stats.categoryCount` / 目录约定 | **静态约定** |
| **应备具体文件 N（现 46）** | inventory 中应备文件条数合计 | manifest `requiredFileCount`（可由 categories 求和兜底） | **清单静态**（手维） |
| **已归集（现 42）** | status=`collected` 的件数 | manifest `collectedCount` | **清单静态** |
| **待补齐（现 4）** | status=`pending`；优先映射 G04 环境相关缺口 | manifest + 回答侧拼接 pending 文件名；G04 仅作说明增强 | **清单静态**（可对照 G04） |
| **当前未闭环问题** | 已发现未整改/复查/销项完成 | `_get_e02_issues_aligned()` / `_e02_open_total()` | **运行时实算**（与首页同源） |
| **历史问题闭环率** | `已闭环 / (未闭环+已闭环)` 字符串如 `a/b` | `_e02_closure_stats()` SQL + open 计数 | **运行时实算** |

**建议调整：** 产品对外说明「11/46/42/4 为资料包编目口径；未闭环与闭环率为平台实时口径」。P2 再做「目录扫描或 DB 动态统计」。

### Q6. 聊天回答结构怎样才合理？旧「只有 KPI 计数」为何不合理？

**结论：** 合理结构 = **证据链叙述 → 11 类进度表 → KPI chips（含未闭环/闭环率）→ PackageCard（下载）→ dataBasis/追问**。仅甩 KPI 计数无法支撑「如何应对检查」——缺类别、缺缺口文件、缺可下载证据包。

**依据：** 现 `build_pack_superior_env` 已按该结构组装；前端 `AssistantMessage` 按 content → kpi → table → packageCard 渲染。

**建议调整：**

- 前端：PackageCard 文件列表避免只显示稀疏 `requiredDocs` 而 chips 显示 46——易矛盾；建议预览「待补齐优先 + 各类代表件」或「查看完整目录见包内 00」。
- 禁止把回答缩成「未闭环 N、待补齐 M」两行无表。

### Q7. 月报表「—」空字段根因与修复原则？

**结论：** 根因是 **字段名映射不全**（`pendingTasks` vs `taskInstances`、责任人多字段）导致行渲染为「—」。修复原则：**无可靠名称/责任人则不展示表**（或只展示有实字段的行），计数仍可来自 summary。

**依据：** `build_monthly_pending` 中 `_pick_str` 多源回填 + `solid_rows` 过滤；`name` 与 `owner` 皆为「—」的行丢弃。

**建议调整：** 若仍见空壳，查当月 `monthly_report_overview` 实际 JSON 字段并补映射；短问「本月月报」需路由到 `monthly.pending`（见 Q10/调整清单）。

### Q8. 「功能验证模式」/DEMO 字样策略？

**结论：** **用户可见助手路径禁止 DEMO/演示/功能验证**；内部可用 `nature: sample`、环境闸、验收 query，但 UI 副标题用中性「合规资料包 · {账期}」。

**依据：**

- 设计红线与实现：包名无 DEMO_；PackageCard subtitle 中性；欢迎/回答无演示字样。
- `?acceptance=1` 仅固定时间戳，不展示「验收模式」铬条。
- 仓库其他模块（碳弹窗、智能入库 demo 适配层）仍有演示文案——**不得带回助手主路径**。

**建议调整：** 校核 checklist 含「助手全文检索 DEMO|演示|功能验证」；内部文档可用 sample，对外话术一律「样例结构 / 占位归档」。

### Q9. 安全包 / 综合包是否应对齐同等 11 类？当前差距？

**结论：** **产品上应有同等「类别化证据链」深度，但目录不必照搬环保 11 类名称**（安全/综合有独立主题）。当前差距大：环保已 00–11 + 46 项编目；安全/综合仍为 **3～4 文件稀疏包**。

**依据：**

| 包 | 目录深度 | 回答表 | stats chips |
|----|----------|--------|-------------|
| 环保 | 00–11，约 46 inventory | 11 类进度 | 齐全 |
| 安全 | `01_清单` / `02_风险台账` / `03_核查表` | 稀疏应备行 + S02 数 | 偏「应备项」旧口径 |
| 综合 | 4 个主题文件夹 | 综合应备清单 | 旧口径 |

**建议调整（P1）：** 安全包按「风险辨识→管控措施→隐患整改→应急演练→费用台账→上级核查」等类别目录化；综合包做「环保摘要 + 安全摘要 + G01/G04」索引包，避免再冒充环保 11 类副本。

### Q10. 后端热更新 / 404「无法连接问答服务」运维教训？

**结论：** 当前 Python HTTP 服务 **不热加载** `assistant_qa.py`；改问答逻辑后未重启 → 旧路由/无路由或连接失败；前端 `askAssistant` 失败则 `fallbackAnswer` 文案为「暂时无法连接问答服务」。

**依据：** `AssistantPage.fallbackAnswer`；`askAssistant` POST 失败再 GET `/api/assistant/qa`；`app.py` 已注册 ask/qa，但进程内模块需重启才生效。

**建议调整：**

1. 改 `server/assistant_qa.py` / `mysql_api.py` 后 **必须重启后端**，再用 curl 验 intent。
2. 区分「未命中意图」（有引导列表）与「服务不可达」（fallback）——勿混为一谈。
3. 交付说明写明：前端 404/网络失败 ≠ 业务空态。

## 3. 证据链完备性评审

**目标证据链：** 审批要求 → 现场实施 → 监测检查 → 问题整改 → 复查销项。

| 环节 | 对应目录 | 完备性 | 说明 |
|------|----------|--------|------|
| **审批** | 01（环评/水保批复及落实） | 弱→中 | 有命名骨架；缺真实批复与条款落实勾选 |
| **实施** | 02 组织制度、03 方案交底、04 日常巡查与设施运行 | 中 | 台账类占位齐全，缺现场原始记录可信度 |
| **监测** | 05 环境监测、06 监理、09 水保生态 | 中（05 有待补齐） | 季报/送检计划标 pending，符合「有缺口」叙事 |
| **整改** | 07 问题整改、08 应急固废危废部分 | 中 | 07 对齐 E02；运行时未闭环数写入说明 |
| **销项** | 07 复查销项、11 上级检查/投诉/处罚整改 | 中偏弱 | 有销项清单与核查表占位；缺真实销项证明扫描件 |
| **总索引** | 00 资料目录及缺失说明 | 强（结构） | 统计与待补齐表清晰，利于校核 |

**弱文件夹（优先加强）：**

1. **01** — 权威源核心，占位感最强。  
2. **11** — 「上级检查通知/处罚」若项目暂无实件，应标注「本期无/不适用」而非伪齐全。  
3. **05 pending 文件** — 目录里仍有 pending 文件名的占位 md，易与「已归集」混淆；应统一「缺文件不放实体 / 或明确 STATUS=待补齐」策略。

**46/42/4 对罗宜高速是否可信？**

- **作为目录演示与结构校核：可信。**  
- **作为项目真实应备黄金数：不可信，须按环评批复 + 水保批复 + 甲方检查清单重算后回写 manifest。**  
- 未闭环与闭环率 **不以 46/42/4 为准**，以 E02 实算为准。
