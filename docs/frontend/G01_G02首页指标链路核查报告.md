## 1. G01 链路核查

### 1.1 首页所见

```text
合规审批与许可
12/12  100%
```

### 1.2 链路图

```text
G01（首页卡）
  ↓ 前端字段
  KpiItem {
    key: 'G01',
    label / fullName ← KPI_HOME_CATALOG.G01「合规审批与许可」,
    value ← API 透传（catalog 不改数值）,
    unit  ← API「100%」（catalog.unit 为空串，不覆盖）
  }
  ↓ API
  GET /api/dashboard/kpis  (source=esg_demo)
    items[G01].value = '12/12'
    items[G01].unit  = '100%'
    items[G01].name  = 库内 kpi_name（V0.3 为「审批合规率」；前端 label 覆盖）
    items[G01].hint  = '12项审批事项全部满足要求。'（V0.3 文案）
  ↓ 发布事实表 / 视图
  VIEW v_esg_demo_dashboard_kpis
    ← esg_demo_indicator_result
       (project_id=1001, period_end=2026-08-04, kpi_key='G01', PUBLISHED)
       value_text = '12/12'
       value_decimal = NULL
       unit = '100%'
       kpi_name = '审批合规率'   ← V0.3 校正
       source_summary ≈ '首页一级指标业务事实校正 V0.3'
  ↓ 二级详情（弹窗，非一级合并计算）
  GET /api/dashboard/kpi/G01
    objects[] objectType = biz_project_approval
    （现网样例：1 条「环评批复」类对象）
```

依据：

- 校准 SQL：`database/current/esg_demo_v0_3/V0_3_001__homepage_kpi_business_fact_calibration.sql`（G01=`12/12`）
- Demo 列表：`esg_demo_api.get_demo_dashboard_kpis` → `v_esg_demo_dashboard_kpis`
- 详情对象：`v_esg_demo_kpi_detail` / 契约表 **`biz_project_approval`**（非现场把 `compliance_procedure`+`permit_record` 求和）

### 1.3 「是否已合并合规审批 + 许可？」

| 维度 | 结论 |
|---|---|
| 展示名称 | **是**（前端 catalog 写成「合规审批与许可」） |
| 一级数值计算 | **否** — 仍是 **单一发布字段** `esg_demo_indicator_result.value_text='12/12'` |
| 是否读取 `permit_record` 并入 G01 | **否**（首页 esg_demo 路径未读该表做 G01） |
| 是否读取 `compliance_procedure` 并入 G01 | **否**（首页一级不读；`mysql_api` 旧路径另有「未完成审批 COUNT」，且当前首页不走该路径） |
| catalog 注释中的「compliance_procedure + permit_record」 | **仅文档意图**，与现网数据路径不一致 |

**重点确认：** G01 **仍然只读取单一来源**（Demo 指标结果表的发布文本 `12/12`）。  
所谓「合并」目前只发生在 **前端展示名**，不是数据合并。

### 1.4 旁路说明（非首页现网主路径）

`mysql_api` 中仍有旧逻辑：

- G01 ← `compliance_procedure` 未完成条数  
- G02 ← 整改台账 / 许可临期等（历史标签混杂）

现网 `source=esg_demo` 时，**首页 KPI 列表不走这套动态 SQL**。

## 2. G02 链路核查

### 2.1 首页所见

```text
重大风险专项方案
2/2  100%
```

### 2.2 链路图

```text
G02（首页卡）
  ↓ 前端字段
  KpiItem {
    key: 'G02',
    label / fullName ← KPI_HOME_CATALOG.G02「重大风险专项方案」,
    value ← API 透传 '2/2',
    unit  ← API「100%」
  }
  ↓ API
  GET /api/dashboard/kpis
    items[G02].value = '2/2'
    items[G02].hint  ≈ '2/2项许可及施工管控事项均已完成。'（V0.3 许可语义）
  ↓ 发布事实
  esg_demo_indicator_result
    kpi_key='G02'
    value_text='2/2'
    kpi_name='许可管控完成率'   ← V0.3
  ↓ 二级详情
  GET /api/dashboard/kpi/G02
    objects[] ← biz_night_construction_record（夜间施工许可记录）
    summaryCards：许可/夜施事项、有效、临期、逾期、待审批
    弹窗标题仍可能为「许可及施工管控」
```

### 2.3 是否来自 `special_plan_approval`？

| 候选表 | 是否被首页 G02 使用 |
|---|---|
| **`special_plan_approval`** | **否**。仅治理接口 `GET /api/governance/special-plans`（现网 total=1），**未进入** `/api/dashboard/kpis` 的 G02 |
| `biz_night_construction_record` | **是**（详情对象主表） |
| `permit_record` | 首页 esg_demo G02 **未**作为一级值来源；详情以夜施记录为主 |
| `compliance_procedure` | **否**（G02） |

**结论：** G02 展示名是「重大风险专项方案」，数值与明细仍是 **许可/夜间施工管控** 口径，**不是**专项方案审批事实。

### 2.4 统计规则（现网实际）

一级：

```text
G02.value = esg_demo_indicator_result.value_text
         = '2/2'   （V0.3 人工/校正写入的完成率表达）
```

二级（详情汇总，由对象状态推导）：

```text
有效 / 临期 / 逾期 / 待审批  ← biz_night_construction_record.permit_status 等
```

**不是：**

```text
COUNT(special_plan_approval) 或 编制/审查/审批/文件关联完成率
```

## 3. 首页数据来源优先级

现网启动顺序（`dashboard.store` → `bootstrapHome`）：

```text
1) GET /api/dashboard/kpis
      └─ esg_demo（当前 source=esg_demo）
      └─ normalizeDashboardKpis：优先 items[] → 组卡片
      └─ applyKpiHomeCatalogLabels：覆盖 label/fullName
           · G01/G02：只改名，不改 value
           · G04：额外演示天数 overlay（V0.4.6）

2) loadEsgHomeStatus（再拉 KPI + 面板/风险）
      └─ 用 API groups 合并状态文案后，再次 applyKpiHomeCatalogLabels

3) API 不可用时
      └─ dashboard.mock / esg-home.mock 兜底
      └─ 仍经 catalog overlay
```

| 来源 | 优先级 | 对 G01/G02 作用 |
|---|---|---|
| **Demo API 发布值**（`esg_demo_indicator_result` / 视图） | **最高（现网生效）** | 决定 `12/12`、`2/2` |
| **catalog overlay** | 高（展示层） | 决定卡名「合规审批与许可」「重大风险专项方案」 |
| **mock**（`dashboard.mock.ts`） | 仅 API 失败 | 备用数值/标签 |
| **静态前端写死合并计算** | 无 | G01/G02 **没有**像 G04 那样的天数 overlay |
| **governance special-plans API** | 与首页 KPI **脱钩** | 不喂 G02 卡 |

## 4. 与 V0.4 设计差异

| V0.4 期望 | 现状 | 差异 |
|---|---|---|
| G01 = 合规审批 **与** 许可合并口径（X/X） | 名是合并，值是单一「审批合规率」`12/12` | **数值未合并许可** |
| G02 = 重大风险专项方案（编制/审查/审批/文件） | 名是专项方案，值是「许可管控」`2/2`，明细=夜施许可 | **名值错配** |
| 数值来自事实表发布 | 一级来自 Demo 结果表文本；专项方案表未进 KPI | G02 应用错表 |
| 前端不写死统计 | G01/G02 透传 API ✓；G04 为演示例外 | G01/G02 无前端假合并（正确），但 API 也未真合并 |

## 5. 下一步修改建议（待确认后再改）

> 本节仅为建议，**本次未改代码**。

### 5.1 第一步：修正数据链路（优先）

1. **G01 发布口径**  
   - 定义「合规审批 + 许可」合并规则（分母/去重/状态）。  
   - 从 `compliance_procedure` + `permit_record`（或既有审批/许可事实）计算后写入 KPI 发布层。  
   - 保持编码仍为 `G01`，首页继续只读发布值。

2. **G02 发布口径**  
   - 一级值改为基于 **`special_plan_approval`**（如已批/应批 → `X/X`，或按编制/审查/审批/文件关联定义）。

   - 许可类旧语义若仍需展示，应归入 G01 合并口径，而不是占 G02 槽位。

3. **禁止**在前端把 G01+G02 数字硬加；合并与专项方案统计应落在 API/发布事实。
