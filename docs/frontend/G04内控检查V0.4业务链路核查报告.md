## 2. 现有数据库能力核查

> 表存在性以 `docs/database/ESG_V0.4数据库实施前结构核查报告.md`（2026-08-04）及现网治理 API 探测为准；本次未再改库。

### 2.1 业务要求 vs 表能力

| V0.4 业务要素 | 期望数据 | 现有表 | 能否支撑 |
|---|---|---|---|
| 内部检查记录 | 检查批次/类型=内部 | `biz_inspection_finding` | **否（表不存在）**；`biz_governance_inspection` 亦不存在 |
| 上级检查记录 | 类型=上级 | 同上 | **否** |
| 审计 / 纪检检查 | 类型=审计/纪检 | 同上 | **否**（无独立审计检查事实表） |
| 整改通知 | 通知/任务下达 | `e_rectification_task`、`rectification_record`、`biz_internal_control_issue` | **部分**：有任务/问题实体，缺「检查类型」维度与 G04 域绑定 |
| 整改完成 | 完成日/完成人 | `e_rectification_task.rectification_completed_*`（V0.4 已加，现网 API 可见） | **部分**：字段已有，但样例任务多为 E01，完成日多为空；**未汇总进 G04 KPI** |
| 累计管理时间 | 开工日→统计日 | 无独立「合规管理起算」事实；S01 用 `value_text` 存安全生产起算日 | **不可复用 S01**；需 G04 自有起算事实或项目开工日字段（另设计） |

### 2.2 重点表逐项

#### `biz_inspection_finding`

- **不存在**（V0.4 结构核查已确认）。
- 无法直接统计「内部 / 上级 / 审计」检查次数。

#### `biz_internal_control_issue`（现网 Demo G04 明细）

- **存在**，约 2 行。
- 字段能力：问题类型/等级、发现时间、状态、期限、关闭时间、证据状态、风险状态。
- **缺口：** 不是「检查过程」台账；无检查主体（内部/上级/审计）、无整改通知编号、无整改完成填报字段；关闭≠整改闭环全流程。

#### `e_closure_case`

- **存在**（约 17 行），配套 `e_case_status_history` / `e_case_evidence` / `e_case_rectification_link`。
- **缺口：** `case_domain` 约束历史上仅允许 E01/E02/E03 类域，**不含 G04 内控检查域**；不能直接把内控检查案件灌进该表而不扩展约束（需单独审批）。

#### `e_rectification_task`

- **存在**（现网治理 API `total=3`）。
- 已具备 V0.4 闭环填报字段：`rectificationCompletedDate` / `rectificationCompletedBy`。
- 现网样例任务标题/编码偏 **E01 环境整改**，与「内控检查」首页语义未绑定；完成日期多为 `null`。
- **结论：** 可作 G04 整改二级数据底座候选，但需「检查→案件→任务」映射与域扩展；**当前不能解释首页「正常」**。

### 2.3 能力总判

| 问题 | 答案 |
|---|---|
| 现有三表能否完整支撑 V0.4 G04？ | **不能完整支撑** |
| 最接近明细的表 | `biz_internal_control_issue`（问题台账，非检查过程） |
| 最接近整改底座的表 | `e_rectification_task` + `e_closure_case`（需域扩展与关联） |
| 最大缺口 | 检查分类事实表（内部/上级/审计）缺失；首页一级值仍是 V0.3 状态词 |

## 3. 首页一级指标建议（仅建议，本次不实施）

### 3.1 优先方案（推荐）

**展示**

```text
内控检查
XXX 天
```

建议正式名称（二选一，推荐 A）：

| 方案 | 首页短名 | 业务解释（给领导） |
|---|---|---|
| **A（推荐）** | 合规管理累计天数 | 自项目开工（或合规管理体系起算日）至统计截止日的累计管理天数 |
| B | 内控检查天数 | 同上，文案更短，但易被理解为「检查活动天数」 |

**计算口径（建议）**

```text
G04天数 = DATEDIFF(统计截止日, 合规管理起算日) + 1
```

- 起算日：项目 **开工日期** 或单独确认的「合规管理起算日」（需写入 **G04 自有事实**，不可借用 S01）
- 统计截止日：与首页其他 KPI 一致的 `period_end` / 业务统计日
- **禁止** 复用：
  - S01 的 `esg_demo_indicator_result.value_text`（安全生产起算日）
  - `s01_confirmation_batch` / 连续安全生产中断逻辑
  - S01 视图里的 `DATEDIFF` 分支（那是安全生产专用）

**依据**

1. 业务确认：G04 不展示状态词；应体现「从开工以来累计管理时间」。
2. 现网「正常」来自 V0.3 状态表达，无法承载检查/整改过程。
3. 展示形态可与 S01「XXX 天」相近，但 **业务来源必须分离**，避免领导追问「天数怎么算」时与安全生产混为一谈。

### 3.2 备选方案（不优先）

| 方案 | 展示 | 为何不优先 |
|---|---|---|
| 未关闭内控问题数 | `N 项` | 接近现网明细，但弱化「累计管理时间」主叙事 |
| 检查完成率 X/X | 比值 | 检查分类表尚未具备，分母定义不清 |
| 继续「正常」 | 状态词 | **明确否决**（与 V0.4 冲突） |

### 3.3 与 S01 边界（必须写清）

| | S01 安全生产天数 | G04 合规管理累计天数（建议） |
|---|---|---|
| 业务问句 | 连续安全生产多久？ | 开工以来合规管理持续多久？ |
| 起算事实 | 安全生产起算 / 确认批次 | **合规管理起算 / 项目开工日（G04 专用字段）** |
| 中断规则 | 可有事故中断重计 | 一般按日历累计（除非另定「管理体系中断」规则） |
| 数据表 | `s01_confirmation_batch` 等 | **禁止共用**；新建或映射项目开工/G04 起算事实 |

## 4. 二级数据展示建议（弹窗 / 工作台）

在一级改为「天数」后，二级建议承载过程与结果（仍属设计建议）：

### 4.1 信息架构

```text
内控检查（G04）
├─ 一级：合规管理累计天数 XXX 天
└─ 二级：
   ├─ 累计检查次数
   ├─ 上级检查次数
   ├─ 内部检查次数
   ├─ （扩展）审计 / 纪检检查次数
   ├─ 整改通知数量
   └─ 整改完成率
```

### 4.2 建议数据映射（实施阶段）

| 二级指标 | 建议来源（实施时） | 现状 |
|---|---|---|
| 累计 / 上级 / 内部检查次数 | 新建检查事实表（或补齐 `biz_inspection_finding` 类模型），按 `inspection_type` 分类 | 表不存在 |
| 审计/纪检 | 同上或独立 `audit_inspection` 类型枚举 | 无 |
| 整改通知数量 | `e_rectification_task`（按 G04 关联过滤）或检查发现→任务链路 | 有表，无 G04 过滤 |
| 整改完成率 | 已完成 / 通知总数；完成判定用 `rectification_completed_date` 或任务状态 | 字段已有，数据未灌满、未接入 G04 |
| 问题清单（过渡） | 可暂读 `biz_internal_control_issue` | 已有，但语义是「问题」不是「检查」 |

### 4.3 与现网治理页边界

- 工作台「治理整改」：`/api/governance/rectification-tasks` — **保持独立能力**，可被 G04 二级引用，但不等于首页 G04 一级口径。
- 首页 G04 弹窗：当前绑 `biz_internal_control_issue`；后续应切换为「检查+整改」聚合，避免继续讲「内控与廉洁问题数」。
